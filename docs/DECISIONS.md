## 2026-09-11: UIを英語1本に。多言語化と自前の翻訳パイプラインを全廃

オーナー判断。理由は2つ。

**① ブランドが割れていた。** earth-trend.com を開いて「世界のトレンド」と書いてあると、
何のサイトなのかが一度ブレる。ドメインと画面の言語が食い違っている状態を解消する。

**② 3言語を維持する根拠が数字に無い。** GA4実測(2026-06-14〜09-11)で
スペイン語ユーザーは **0人**、英語84人、日本語116人。一方で es は翻訳ジョブ全体の約34%を占めていた。
そもそも89日で204ユーザー・自然検索3セッションなので、**言語を足しても引いても流入は動かない**。
よって言語は「成長のため」ではなく「維持コストのため」に決めるのが正しい、と整理した。

### 判断: 翻訳はブラウザのGoogle翻訳に委ねる

2026-06-14 の i18n 設計は「メインのグラフはCanvasだからブラウザ翻訳が効かない ⇒ 自前i18nが必要」
としていた。**この前提はもう成立しない**: 当時の主役だったグラフは `/analysis` だけになり(全PVの7%)、
いまの主役であるトップと国ページは**全部HTML**。しかもトレンド語には既に `translate="no"` が付いている。

つまりブラウザ翻訳をかけると「原語は生のまま残り、周りだけ母国語になる」= PHILOSOPHY の
「原語の生の文字は常に残す」がそのまま実現する。しかも3言語ではなく100言語以上で、維持コストゼロで。

### 捨てたもの

- `lib/i18n.ts`(319行)・ロケール辞書 ja/en/es・`[lang]` ルーティング・hreflang・言語切替UI
- 翻訳パイプライン一式: `lib/translate.ts`・`lib/ratelimit.ts`・`/api/translate`・
  `WordGloss`・`NewsTitle`・cronの翻訳warming・world blob の `tr` フィールド
- 死にコード: `LandingPage`(旧トップ)・`components/landing/`・`[lang]/trends/`
- 差し引き **約1,300行の削除**。gtxという非公式エンドポイントへの依存が消えたのが一番大きい

### URL

ロケール接頭辞を廃止。`/ja` `/en` `/es` 接頭辞と `/trends` は301で正準URLへ。
`next.config.ts` の rewrites は不要になり redirects だけになった。
**いま構造を変えるコストはほぼゼロ**(自然検索が3ヶ月で3セッション=失うものが無い)という点も判断材料にした。

### 失うもの / 判断を保留したもの

- **語そのものの訳(WordGloss)が消える**。`translate="no"` で守っているので、ブラウザ翻訳もここは訳さない。
  語を2回描いて片方だけ `translate="no"` にすれば原語と訳を両方出せるが、翻訳OFFの読者に同じ語が
  2回見えるため、DOM差分で出し分けるハックが要る。今回は入れていない。ニュース見出しは訳されるので
  文脈は取れる、という判断。
- sitemap の `lastmod` を実際の更新境界(30分)に修正。`/analysis` は `noindex,follow` に(seed付きURL対策)。
- `mergeGeo` は前回blobを**明示的なフィールド選択**で引き継ぐようにした。spreadのままだと旧スキーマの
  `tr` が blob に載り続け、クライアントへも送られてしまう。これで1サイクルで形が揃う。

## 2026-09-11: ストレージを「1キー1blob」へ再設計(無料枠の恒常消費を37%→1%に)

Upstash無料枠の実際の制約は **50万コマンド/月・256MB・帯域10GB/月**(帯域は従来の記録に無かった)。
旧構成は無人でもサイクルあたり約128コマンドを消費しており、**誰も来ていない状態で枠の37%**を
使っていた。集客する前にここが折れる構造だったので、蓄積の持ち方から作り直した。

### 判断

このデータはDBワークロードではなく「**30分ごとに書き換わる1個のJSON**」(24カ国で実測340KB)。
それを国別×ティック別×語別のキーに分解していたのが消費の正体だった。`world:v1` に畳む。

| | 旧 | 新 |
|---|---|---|
| 書き込み | `snapshot:<geo>` ZADD ×24 + `latest:<geo>` SET ×24 + trim + 翻訳SET | `SET world:v1` 1回 + 細い履歴のRPUSH |
| 読み取り | `ZREVRANGE` ×24(独立24往復) + 語ごとの翻訳GET(1周期最大約930往復) | `GET world:v1` 1回 |
| 1サイクル | 約128コマンド | **4コマンド** |
| 月間(無人) | 約18.4万(枠の37%) | **約6千(枠の1%強)** |

**読み取りが閲覧量に比例しなくなった**のが本質。訳を同じblobに焼き込んだので、国別ページの
描画でRedisを追加で叩かない。

### 副次的に直ったこと

- **翻訳の取りこぼしが回収されるようになった**。旧実装の温め対象は「前回スナップショットに
  無かった新規語」だけで、上限や時間切れで溢れた語は二度と対象にならず、バックログを埋める
  経路が存在しなかった(`a64f6a5` で全項目ローテーションにしたのを `23316ba` でコスト理由に
  戻した際の副作用)。訳がblobに同居する新構成では、未解決スロットが次サイクルのblobにも残り、
  予算内で再挑戦され続ける。
- **gtxの実呼び出しが想定どおりになった**。旧 `WARM_CAP` は**成功数**を数えていたため、訳が
  原語と同じになる語(固有名詞=トレンド語では常態)が続くと上限に達せず、deadlineまで回って
  実呼び出しが想定の4〜6倍(約5,000〜9,600回/日)になっていた。上限を実呼び出し回数に変更し、
  「訳不要」は `""` を記録して二度と試さないようにした。
- **トップのRSCペイロードが 345KB → 48KB**。`CountryTile` はクライアント境界なので、射影しないと
  表示されないニュース(見出し・URL・媒体名)まで全24国分が直列化されていた(`getGalleryTiles`)。
- ニュース見出しの訳もSSRで渡るようになり、クライアントからの `/api/translate` がほぼ不要に。
  国ページ1枚で最大60回叩いていた(IP制限80/分)ため、スワイプで隣国へ移ると枯渇していた。
- `redisEnv`/`redis` の4重複を `lib/redis.ts` に集約。

### 失うもの / 移行

- `snapshot:<geo>` の300件ZSET(過去約6日)は使わなくなる。代わりに `hist:<YYYY-MM-DD>` へ
  `{語, traffic, firstSeen}` だけを1サイクル1件RPUSH(newsを落とすので容量は約1/5、TTL 30日)。
  「④時間(velocity可視化)」の余地は残す判断。
- デプロイ直後は `world:v1` が空なのでRSS直取得から始まり、各国10件程度になる。running union が
  積み上がって通常の20件前後に戻るまで**2〜3時間**かかる。
- **旧キーの掃除が必要**(放置すると約50MBが256MB枠に residual で残る)。Upstashコンソールか
  REST で1回だけ:
  `DEL snapshot:JP … snapshot:IT latest:JP … latest:IT`(DELは複数キーで1コマンド)。
  `tr2:*` はTTL 30日なので放置で消える。

## 2026-06-14: 海外対応(i18n＋コンテンツ翻訳)の構造を確定(マーケ最適)

オーナーが「マーケ最適な構造に」と判断を委任。海外で"発見される"ことを最優先に、以下で確定:

**A. UIロケールは `[lang]` ルーティング(ja/en、各言語を個別URL)**
- `/en/jp` のように lang×geo を直交させる(英語UIで日本のトレンド)。middlewareで初回 Accept-Language 判定→該当ロケールへ。`generateMetadata` でロケール別 title/description＋hreflang、`<html lang>`、sitemap両対応。
- クッキー/Accept-Languageのみ(URL不変)は1URL=1言語扱いでSEOに弱く**不採用**。per-locale URL でこそ各言語市場の検索流入が立つ。

**B. コンテンツ翻訳は「原語＋訳の併記」。原語の生の文字は常に残す**
- ネイティブ語に `translate="no"` を付け、ブラウザ翻訳でも置換されないよう保護。その上で**我々の訳を注釈として添える**(例「futebol → サッカー」)。バブルの壁は原語のまま(芸術を崩さない)、訳はまず詳細パネル(理解したい時)に出す。ニュースは訳す。
- マーケの核: 「世界中のリアルタイム検索を母国語で覗ける(でも生の文字も見える)」=他にない体験=シェアされる。AとBは噛み合う。
- 翻訳エンジン: **オンデマンド＋Upstashキャッシュ**で実消費を極小化。MVPは **MyMemory(キー不要・無料)**、品質を上げたければ後で **DeepL無料枠** に差し替え。コストほぼゼロ・放置で回る([[project-earth-trend-search-only]]の制約に整合)。

**C. UIガワは {ja,en} 辞書。国名も訳す(日本→Japan)。** グラフのノード語=コンテンツなので原語のまま(Canvasでブラウザ翻訳も不可だが、探索の本質なのでOK)。

**実装順**: ①コンテンツ翻訳(詳細パネル・原語＋訳) → ②UI辞書ja/en → ③`[lang]`ルーティング＋SEO。①から出すと手応えが早い。
旧設計メモ(下記2026-06-14「多国籍対応(i18n)の設計方針確定」)はこの決定で具体化・更新。

## 2026-06-14: earth-trendは「検索エンジンの普遍的注意」のみ(コミュニティ横断は別プロジェクト)

オーナー判断。検索(Google等)は誰もが使う＝母集団バイアス最小の普遍的な好奇心シグナル。
Wikipedia/Reddit等は対象範囲が狭くトレンドが特定母集団に左右されやすい→ "earth-trend(地球=普遍)" のブランドに合わない。コミュニティ横断・特定領域の可視化は別プロジェクトに切り出す(アイデアは温存)。
- **データ源は検索系に限定**(Googleトレンド急上昇RSS、Googleサジェスト)。
- **重要な帰結**: 検索は「全検索に占める割合(part-to-whole)」を無料公開しない(出すのは相対関心0-100と急上昇=velocityのみ)。→ **真のツリーマップ(面積=割合)は誠実に作れず不採用。** trendingの正直な魂は magnitude より **velocity(勢い)・recency(発生時刻)**。規模表現は「全部ではない」と分かるパック円に、本命は④時間/勢い(スパークライン)に寄せる。
- Googleトレンドの急上昇RSSは1国あたり約10件のみ(JP実測10件、approx_trafficは粗いバケット)。"全体の分布"ではなく"急上昇の上澄み"である点を表示でも誠実に扱う。
- 詳細: [[project-earth-trend-search-only]]

## 2026-06-14: データ次元の深化ロードマップ確定(①リスト見やすく → ④時間 → ③文化)

哲学(docs/PHILOSOPHY.md「つながりの4次元」)のうち、今あるのは①連想(サジェスト)だけ。
informationisbeautiful の強い型(驚き・比較・規模・時間)に照らし、未開拓の規模/時間/文化を本命に育てる。
オーナー判断の着手順:

1. **①リストビューを"見やすく"(玄関の底上げ)** — トレンドページに Google Trends 風の全画面で見やすい別表示を追加。最も見られる面・retentionの習慣surface・最速の勝ち筋。各語クリックで分析グラフへダイブ(既存導線と接続)。
   - **デザイン方針の線引き**: これは「装飾」ではなく「情報設計＝見やすさ・規模(traffic)の可視化」として作る。配色/質感の作り込みは[[feedback-no-early-design]]どおりデザインフェーズまで保留。素のHTML+最小クラス。
2. **④時間(蓄積データ)** — Upstashに既に貯まっている時系列(`snapshot:<geo>` ZADD、`firstseen:<geo>`、30分毎GitHub Actions)を可視化。注意の上昇/消滅/回帰のリズム。取得コストゼロで"準備ができている"唯一の次元。richnessは履歴の長さに比例(蓄積開始2026-06-13)→今作って貯め続けるのが正解。読み取りAPIは未実装(`snapshot:`/`firstseen:`/`latest:`を読む)。

## 2026-06-14: 多国籍対応(i18n)の設計方針確定 ※設計のみ・実装は未着手

英語圏流入を取りに行くための国際化の方針を先に確定する(実装はデザインフェーズ/機能確定後に判断)。

### 前提となる重要な技術的事実
- **メインのグラフはCanvas描画 → ブラウザのGoogle翻訳が一切効かない。** よって「翻訳に任せる」戦略は不成立。アプリ側で言語を出し分ける真のi18nが必要。
- 逆にこれは長所でもある: **トレンドワード(各国の生の検索語)は絶対に翻訳してはいけない**(「だんじり祭」は "Danjiri Festival" のまま見せたい)。Canvasが翻訳不能なことが、生の検索語の保全を自動的に保証している。
- データ層は既に多言語対応済み: `GEO_HL`(国→サジェスト言語)で各国語のデータを取得している。**残る作業はUI文言とメタデータだけ。**

### 国際化すべき2つの独立した軸(混同しない)
1. **UIロケール** — ナビ/ボタン/About等の表示言語。ユーザーが読む言語。
2. **データロケール** — どの国のトレンド(geo)/どの言語のサジェスト(quest)を見るか。
- この2軸は**直交させる**。日本語UIのユーザーが米国トレンドを見られるし、英語UIのユーザーが日本のトレンドを見られる。UIロケールとデータ選択を連動させない。

### 作業規模(2026-06-14時点の実測)
- 日本語UI文字列リテラルは **約43箇所・UI 12ファイル**。デザインフェーズ前で文言が最小の**いまが辞書化の最安タイミング**。
- 翻訳されては困る箇所(トレンド語)はそもそもデータなので辞書化対象外。

### 採用する設計
- **辞書方式**: `{ ja, en }` のキー辞書に文言を集約。3言語目以降は列を足すだけ=限界費用小。
- **ルーティング**: SEOを取りに行くならサブパス(`/en/...`、既定jaはルート)。`hreflang`相互リンク・locale別`generateMetadata`・locale別sitemapまでセットで初めて検索流入に効く。UI辞書だけなら`?lang=`でも可だが、SEO効果は薄い。
- **言語判定**: 初回は`Accept-Language`、以降は明示選択を永続化。データ軸の`geo`/`lang`パラメータとは別管理。
- **メタデータ/OG**: title/descriptionをlocale別に。OG画像はラテン文字のみなので現状のまま流用可。

### フェーズ
1. **ja+en 2言語**(推奨の出発点): 辞書化+英語版。英語圏ポテンシャルが最大。
2. SEO本気化(サブパスルーティング+hreflang+メタデータ多言語)。
3. 3言語目以降は辞書に追加するだけ(翻訳品質チェックのみ人手)。

### 未決事項(実装着手時に判断)
- 着手タイミング(デザインフェーズ前 or 機能確定後か)。
- サブパスルーティングまでやるか、UI辞書だけに留めるか(=SEOにどこまで投資するか)。
