# スケール設計方針

実装は安い(AIに任せる)。資産は「ページを安く量産できる構造」と「何を足すかの選定眼」。
このサイトのスケール軸は3つで、それぞれの現在地と引いてある境界線を記録する。

## 軸1: ツール追加のスケール
- **境界線**: エンジン(`src/lib/convert.ts` `zip.ts` = 純粋関数) / ページ(`src/app/<slug>/`) / レジストリ(`src/lib/tools.ts`)を分離済み
- **ツール追加の手順**: ① `tools.ts` に1エントリ ② `src/app/<slug>/page.tsx` を1枚 ③ 必要ならlibにエンジン追加。トップのカード・sitemap・構造化データは自動で追従する
- URLは `/<slug>` で恒久。一度公開したslugは変更しない(SEO資産)

## 軸2: ページ量産のスケール(pSEO)
- **最終形**: 規格＝データ、ページ＝テンプレ。「規格定義レコード追加→ページ自動生成(generateStaticParams)」でコードを書かずにページが増える状態
- **意図的にまだ作らない**: サンプルが1個(LINEスタンプ)しかない段階で汎用スキーマを設計すると外す。同人入稿(塗り足し・dpi検査)は検証ロジックの形が別物の可能性が高い。**2個目のツールを書いた時点で共通部を抽出し、3個目からデータ駆動化する**(Rule of Three)
- それまでの規律: ページに規格値をハードコードしない(`src/lib/specs.ts` のような定数モジュールに分離しておく)

## 軸3: 意思決定のスケール
- 「次に何を足すか」はGSCのクエリデータ駆動(表示されているのにページがないクエリ→追加)。勘で足さない
- ローンチ時必須: GSC登録・sitemap送信(自動生成済み)・Vercel Analytics
- ニッチ選定の判断基準は `DECISIONS.md` 末尾の4項目を使う

## 不変条件(全ツール共通の制約)
1. ファイルはサーバーへ送らない(全処理ブラウザ内) — 責任設計でありプロダクトの売り
2. 出力は機械的変換のみ。助言・判断・保証を出力しない
3. ランニングコストを増やす依存(外部API・DB・認証)はフリーミアム判断まで導入しない
